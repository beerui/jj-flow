# end — Git 收工（提交、推送与合分支）

当你的功能代码已经改完并通过验收后，`end` 帮你**一次性做完标准的 Git 收尾动作**：
**拉取最新远端 → 只提交本任务涉及的文件 → 同步并推送工作分支 → 切换到集成分支（如 `dev`）同步合并并推送 → 安全切回你的工作分支。**

它的职责边界非常纯粹：**只操作 Git**，不修改业务代码、不替你归档 `ralph` 任务、也不改动 `dispatch` 调度账本。

| 宿主工具 | 调用写法 |
| :--- | :--- |
| **Codex** | `$jj-end` |
| **Claude Code / Grok / Qoder** | `/jj-end` |

*(注：在对话中直接说“收工”、“合到 dev”、“结束任务提交并合并”也会触发本工作流。)*

## 一、适用场景与边界

**什么时候用 `end`：**
* 单仓 `ralph` 任务已经开发验收完毕，需要把改动正式提交、推送并合并到 `dev` 分支。
* 多项目 `dispatch` 调度已全部显示 `VERIFIED`（验收通过），现在需要到各个仓库把本地代码真正推送并合入远端集成分支。

**什么时候别用 `end`：**
* 只是写到一半想在本地临时存个档（自己执行 `git commit` 即可）。
* 代码还没验收完、或者当前环境禁止 `git push`（此时可使用 `$jj-end dry_run=true` 只看预览计划）。

## 二、开始前准备

1. **确认当前在你的功能工作分支上**：`end` 要求当前所在的分支就是本次任务的工作分支（如 `feat/password-expired-tip`），**不会在收工前擅自替你切换工作分支**。
2. **清楚要合入哪条集成分支**：
   * 如果你不指定，默认按 **`dev` → `develop` → `main`** 的顺序，自动选择仓库里第一个存在的分支作为合入目标。
   * 如果你想合入预发分支（如 `staging`），**必须显式写出 `integration=staging`**（仓库里存在 `staging` 分支、或历史 `git log` 里有过 `Merge into staging`，都**不会被当作**默认合入依据）。

## 三、标准执行流程（6 步安全收尾）

当你发送 `$jj-end` 后，Agent 会调用内置的批处理脚本，按以下固定顺序安全执行：

| 步骤 | 执行动作 | 安全保障说明 |
| :--- | :--- | :--- |
| **1. 打印收工计划** | 先在对话里输出一行计划：`工作分支 → 合入分支（依据：…）` | 让你一眼看清要把哪条分支合到哪里；若发现不对可当场拦下 |
| **2. 拉取与范围校验** | 执行 `git fetch`，核对工作区改动文件清单 | **只提交属于本次任务的文件**；无关的未跟踪临时文件、密钥或脏子模块会被明确列出或阻断，绝不一锅端 `git add .` |
| **3. 提交本任务代码** | 生成规范的中文提交信息（如 `feat(login): 新增密码过期提醒弹窗`）并提交 | 若工作区已经干净（此前已手动 commit），则自动跳过本步 |
| **4. 同步并推送工作分支** | 将工作分支与远端同步（优先快进合并）并 `git push` | 确保远端工作分支备份最新代码 |
| **5. 切换到集成分支合并推送** | 切换到 `dev`（或你指定的集成分支），同步最新远端后将工作分支合并进来并 `git push` | 严格遵守**“只把工作分支合进 `dev`，绝不把 `dev` 反向合进工作分支”** |
| **6. 切回工作分支并汇报** | 自动切回你的功能工作分支，输出一行最终收工结果 | 只有工作分支和集成分支**双双推送成功**，才会报告收工完成 |

## 四、完整端到端实战示例

### 示例 1：日常默认收工（合入 `dev`）

```text
你：
$jj-end

Agent：
收工计划：`feat/password-expired-tip → dev`（依据：默认存在 `dev` 分支；待提交文件 2 个：`src/views/login/LoginForm.vue`、`tests/login.spec.js`）
正在执行 Git 收尾（fetch → commit → push feat/password-expired-tip → merge & push dev → return）……

已合并：feat/password-expired-tip → dev · 当前在 feat/password-expired-tip
```

### 示例 2：只看预览计划，不实际改动 Git（`dry_run=true`）

如果你不确定它会提交哪些文件、合进哪条分支，可以先跑一次只读预览：

```text
你：
$jj-end dry_run=true

Agent：
【收工预览（dry_run=true，未修改仓库）】
- 工作分支：feat/password-expired-tip
- 目标集成分支：dev（依据：默认规则）
- 拟提交文件：
  1. src/views/login/LoginForm.vue
  2. tests/login.spec.js
- 完成后返回分支：feat/password-expired-tip
```

### 示例 3：显式指定合入 `staging` 分支

```text
你：
$jj-end integration=staging

Agent：
收工计划：`feat/password-expired-tip → staging`（依据：用户显式指定 `integration=staging`）
已合并：feat/password-expired-tip → staging · 当前在 feat/password-expired-tip
```

## 五、遇到合并冲突或异常时怎么处理？

| 遇到的情况 | `jj-end` 的处理机制 |
| :--- | :--- |
| **合并到 `dev` 时遇到代码冲突** | 不会一见到冲突就盲目放弃，也不会只解一半留半成品：<br>1. 先将冲突文件分类为 **可自动合并（`self-merge`）** 与 **需人工裁决（`unhandleable`）**。<br>2. **两边各自新增独立代码/样式/文档**：自动合并保留双方改动、验证无冲突标记后继续完成推送。<br>3. **同一产品开关两边相反、或涉及密钥/二进制文件**：立即执行 `git merge --abort` 完整回滚本次合并、切回工作分支，并把冲突分类表交给你决定。 |
| **远端推送失败（如网络断开或权限不足）** | 立即停止后续步骤、保留当前已完成的本地状态并停在工作分支，如实把远端报错信息展示给你，绝不会谎报“已收工”。 |
| **你在做完实现后暂时不想推远端** | 如果你在指令中说明了“先别推”或“只提交不推送”，Agent 就不会自动发起远端合并。 |

## 六、安全红线（绝不触碰的操作）

为了保护团队仓库历史，`jj-end` 严格遵守以下红线：
* **绝不**执行 `git push --force`、绝不删除分支、绝不修改全局 Git 配置。
* **绝不**默认使用 `git pull --rebase` 改写提交历史（除非你显式要求）。
* **绝不**使用整文件 `--ours` 或 `--theirs` 粗暴覆盖冲突文件。
* **绝不**把 `dev` 集成分支反向合并进你的功能分支。
