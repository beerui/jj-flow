# Changelog

版本标题附带发布时间（`YYYY-MM-DD HH:mm`，与发版 commit 本地时区一致）。进行中的变更写在 `Unreleased`；无待发布条目时写「暂无」。

## Unreleased

- **`docs:check` 修好：更新日志改为投影，站点页面不再写 include 指令**：`docs:check` 在 main 上一直是红的——93,032 字节的更新日志页正好在 VitePress 打包阶段的内存墙上，默认 4 GB 堆耗尽，报的是一段看不懂的 native 栈。根因不在页面积，在一行示例代码：`docs/design-docs/docs-site-vitepress.md` 的文件树清单里写了 include 指令当例子，而 VitePress 的 include 是正则替换、不认代码块；又因为 Windows 的 NTFS 大小写不敏感，`../CHANGELOG.md` 解析到的就是 `docs/changelog.md` 自己，那一页再递归包含根 `CHANGELOG.md`——两页各带一整份更新日志，正是切分要避免的那件事。修法是两件：两页改由 `scripts/sync-changelog-pages.mjs` 从 `CHANGELOG.md` 的两个区域投影并签入仓库（`CHANGELOG.md` 仍是 release-please 的唯一来源，正文一字不改），`scripts/check-changelog-split.mjs` 查五件事——区域标记成对且闭合顺序对、没有版本标题掉队、两页等于投影、每页在 80,000 字节预算内、**站点页面里一行 include 指令都不许有**（它能不能解析取决于文件系统大小写敏不敏感，那不该由运气决定）。构建从 OOM 变成 20.96 秒。
- **`jj-team` 快照陈旧检测补上环境指纹，「skill 树变了」与「环境变了」不再混为一谈**：staleness stamp 看的是 skill 树，而团队所处的环境变得更快，且后者的变化一个 mtime 都看不见——宿主升级了某个 agent 的模型、`rebuild` 重写了 `roles[].model`、项目换了依赖或发布面，skill 目录里没有任何文件动过，而缓存里的人设提示词描述的是一个已经不存在的团队。`snapshot_stale.mjs` 因此在 stamp 之外多发一个 `environment-fingerprint v1` 块：四节 `derived`（模型面 / 栈 / 发布面 / 约定）由脚本从盘上现算，三节 `declared`（能力 / 花名册 / 维度）来自 `team-session.json`；两半各自回答「环境动了吗」与「台账还说着快照声称它说的话吗」，报漂移时点名属于哪半截——修法不同，前者是世界变了，后者是 `rebuild` 之后缓存描述的是一个不存在的团队。digest 是 sha256，覆盖除 `generated_at` 以外的全部规范文本，**先验 digest 再比信号**：对不上说明块被改过，那是「无法验证」而不是「陈旧」，否则一句「重新生成」就把这次改写洗成一次干净的新鲜盖章。`declared` 投影**故意不含** `last_seen_at` 与 `tasks[]`——两者每次被碰到都变，纳入指纹会让它每执行一次就漂一次，而每次执行都叫的守卫等于没有守卫。没有 fingerprint 的快照一律判 `2`：`0` 是调用方唯一会照着行动的码，一个对自己更容易过期的那半截只字不提的快照，不能有能力产出它。`--stamp` 原先禁止与 `--team-dir` 同用（理由写的是「它什么都不检查，所以没有目标可指」），而 `declared` 半截只能从台账读，于是收紧的是禁令本身而不是新增旗标：只禁 `--snapshot`，放行 `--team-dir`；不带 `--team-dir` 时仍只发 stamp 块并在 stderr 说明，老调用方式不变红。14 行畸形字段表逐行固定指纹的每种坏法，与 stamp 那张表同一种写法。上一条（快照机械化）列举的 `2` 成因因此从三种扩到六种，新增的三种是：没有 fingerprint、digest 与自己的内容对不上、指纹记录的项目路径已不在。合约：`tests/jj-team-snapshot-stale.test.mjs`、`tests/jj-team-contract.test.mjs`。
- **`jj-team` Phase 3 补上环境探测，花名册的另一半不再靠猜**：并行度回答「几个座」，Phase 3 回答「座上坐谁」。后者不是偏好问题而是可达性问题：宿主摸不到的模型写进 `roles[].model` 不是一个计划，是一把空椅子，而且团队是在 spawn 那一刻才发现，台账已经先声称了它有。六路信号，每路只许决定一件事——宿主能力定并发还是串行，**不改哪些模型存在**；可达模型面（本会话模型 + 宿主读的 agent 定义文件 `agents/` / `.grok/agents` / `.codex/agents`）定 `roles[].model` 能写什么；项目栈定 reviewer 要看得懂什么，**不定谁看**；发布面定哪些文件在审查范围内，**不定谁审**；已有约定定状态与 findings 落在哪，**不定什么是好活**；并行度定几个座，不否决预置。**这是模型上下文，不是新命令面**：它在会话里执行，不新增 CLI，产物写进台账——也就是环境指纹的 `declared` 那半截，让「探测写了什么」与「快照声称什么」从此是同一份事实。报告格式固定，其中 `excluded` 行是承重墙：只报纳入了什么的花名册，和根本没探就给出的花名册，从产物上分辨不出来——两者都是一个像样的花名册，只有一个是诚实的；所以每一道被计成 0 的道、每一个摸不到的模型面，都必须在这行里带着理由出现。然后点一次头就停：不二次定规模、不问用户想要哪些角色、不重开探测刚刚关掉的决策。摸不到时不静默映射到默认值，如实报并按报出来的排。合约：`tests/jj-team-contract.test.mjs`。
- **`jj-team` 审查维度分成底线与项目两层，项目维度只能由探测指到**：原规则「四项通用维度，不按项目另发明」对漂移的判断是对的，执行方式却阻断了它要防的那类审查——当一个项目的契约真的长在底线看不见的地方（SDK 的第二个消费者、带日期的迁移、把两道并行变成一道串行的宿主能力），reviewer 手里没有任何可打分的东西，那条契约就退化成凭眼睛看。底线仍是那四项，仍不可谈判、不可删、不可改权重；项目维度（`PD-<n>`）只能由 Phase 3 探测指到才加，记 id / 名字 / 权重和自己的 STRONG / ADEQUATE / WEAK 锚点，与底线维度同样一票否决——加它就是为了能在它上面否掉一个改动。六路信号各自能许可什么、以及「已有约定」这一路什么都许可不了，写成映射表固定下来：它决定状态落在哪，不决定什么是好活，而它恰恰是最容易被抻成一个维度的那一路。多数项目探完发现底线没漏东西，`project: []` 就是正常结果——这不是没找，是找了之后确实没有。`team-session.json` 记成 `{floor[], project[], all[]}`，`all` 是 `floor` 后接 `project`；裸数组仍读作「只有底线、没有项目维度」，改形状之前的旧台账照样过检。合约：`tests/jj-team-contract.test.mjs`。
- **`jj-team` 快照陈旧检测机械化**：`team-snapshot.md` 头部的 staleness stamp 此前只是散文规则，由人眼比对。新增 `skills/jj-team/scripts/snapshot_stale.mjs` 复读每个登记路径，以退出码回答：`0` 一致、`1` 陈旧（点名改了哪个文件）、`2` 无法验证（没有快照、stamp 读不出、skill 路径已不在）——**无法验证与通过是两回事，故单独一个退出码**；第四个码 `3` 用法错误（命令本身打错，于是什么都没检查）是随后补的，见下条。stamp 记录的是**已加载 skill** 的宿主路径（业务仓里没有 `skills/jj-team/`）与其各文件 mtime，mtime 由 `--stamp` 产出、禁止手写；skill 文件在快照后新增或删除同样判定为陈旧，纯 mtime 比对看不见这一类变化。该检查接入 Phase 0 / `check` / `resume` 三个原本靠肉眼信任快照的调用点。收尾关掉的是**这一类**而不是两个实例：17 行畸形字段表逐个钉住 stamp 的每种坏法，每行带 `without` 记下加校验之前它读成什么——`yesterday-ish` 读成 fresh、`skill_root` 指到文件时读成 stale，都是曾经会静默给出错误答案的行；`--skill-root` 与 `--snapshot` / `--team-dir` 的冲突也由一条规则收口（`--skill-root` 只告诉 `--stamp` 去哪读），不是补第四个 `if`。合约：`tests/jj-team-contract.test.mjs`、`tests/jj-team-snapshot-stale.test.mjs`。
- **`jj-team` 并行度公式排除 team-lead 自有的道**：在飞改动归 team-lead 本人时没有可派对象，计入道数会让 `implementers = measured lanes` 推出一个闲着的 implementer，正是该公式防腐条款要盯的失败。现与「卡在决策上」同级排除，记入 `parallelism.excluded`；公式本身不变，改的是道数的定义，不是在公式旁再开一个例外。同一事件的范本随之改正：`SKILL.md` 的 worked example 与 设计文档 §12 首条原先给出「team-lead + 1 implementer + reviewer」，在那唯一一条道的 owner 是 team-lead 时与该条目自相矛盾，现按 `implementers = 0` 陈述，并由合约测试钉住（范本不套公式同样算漂移）。合约：`tests/jj-team-contract.test.mjs`。
- **`jj-team` 团队账本落点改为项目级 `.workflow/.team/`**：主落点为 `<main checkout>/.workflow/.team/TEAM-<project_key>-<date>/`，与三个 sibling 引擎（`TC-*` / `TLV4-*` / `TAS-*`）同一根，一条约定覆盖四个引擎；它也改变了 key 猜错时的失败形态——Phase 0 的 glob 什么也找不到，于是重新预置，而不是静默落进一个属于别的项目的、看起来很正当的 home 目录。主 checkout 由 `git rev-parse --git-common-dir` 解出，用 `path.resolve(cwd, common, '..')` 而**不是** `dirname(common)`：在主 checkout 上该命令返回的是相对路径 `.git`，`dirname` 会得到 `.`，正好指向当前 worktree——linked worktree 的 `.workflow/` 是另一个目录，账本会被劈开，而这条 glob 会因 cwd 不同找到零个或两个团队。`~/.jj-flow/team/TEAM-<project_key>-<date>/` 保留为**显式降级根**，理由是机械的而非偏好的：`harness-manifest.json` 的 `record_system.forbidden_paths` 含 `.workflow`，`scripts/check-harness.mjs` 的 `HNS-STATE-001` 会在该路径一出现就让 `harness:check` 变红，本产品仓正是被自己的闸门推回落级根的那一个。`$JJ_FLOW_HOME` 此后只影响降级根，不再整体搬迁——文档里「可整体换个位置」那句话必须改掉，留一句做不到的承诺比没有承诺更糟。**此条取代 0.2.7 中「团队状态落 `~/.jj-flow/team/<project_key>/`……`$JJ_FLOW_HOME` 可整体覆盖」的陈述**（按 release-please 惯例，已发布段落保持历史原样，以新条目为准）。

- **`jj-team` 的 `<project_key>` 不再被重新发明**：此前有三种推导表述且没有一种等于代码。现唯一实现是 `resolveProjectKeyFromCwd(cwd)`（`src/projectMap.mjs`），spec 的 Step 0 点名它、不再复述算法——与「阶梯只有一份」同一条纪律。硬理由不是「团队也这么叫」：同一个 key 还命名 `~/.jj-flow/memory/<project_key>.md`，两处名字分叉会让记忆与团队互相找不到。jj-team 路径上目前没有任何运行时调用方，所以此处不得声称有。
- **`jj-team` 陈旧判定退出契约补齐为四个码**：`0` 一致 / `1` 陈旧 / `2` 无法验证 / `3` 用法错误。8 处完整枚举由合约测试钉住；另 2 处（`SKILL.md` 的 `check` 行与错误处理行）只提 `1` 与 `3` 两个码，措辞自洽、是子集，不声称是枚举，故不钉。`references/team-manual.md` 的 Recover 行从「不钉」移到「必须钉」：它是 `resume` 调用点，四码少一个不是措辞缺口，是 resume 给出错判。上一条（快照机械化）原先只列三个码，已补第四码并注明它来得较晚。
- **`jj-team` 的单源纪律从「声明」变成「被守」**：`SKILL.md` 一边写「解析表只有一份……不要在此复述」，一边在 `:143` 复述主 checkout 公式、在 `:211` 复述 R1–R6——被它自己声明为单源的两条规则，在同一个文件里各有一份副本。公式在 6 处出现而**实现为零**：产品里没有任何代码解析团队根，所以没有任何断言能机械判它对错；原断言是「文件内任一出现即算」，改坏 spec 的操作行会被 spec 自己的解释行喂饱（M1 实测存活 26/26）。处置因此不是加短语断言，而是**删复述、改指针、断言只守结构事实**：`state-layout.md` 公式副本数恰为 1 且 `dirname(common)` 不出现，`SKILL.md` 必须含指向 spec 的指针且自身不复述，Lifecycle 的 Phase 0 行不得把 provisioning 当作一个分支（R6 之后明写兜底条款，表格是完备的）。注释里如实写下守不住什么：**公式正确性没有机械保证**（无实现可测），且 spec 之外还有 4 处复述（设计文档两处、命令页、本文件）不在守卫视野内。变异 M1 / M2 / O1 逐个整行替换重放，全部被杀（26/27，且由点名的断言杀，不是顺带）。
- **`jj-team` 陈旧判定的两个条件一起定义，不可判的那个降级为只报不判**：原来一句话「`> 14d` 且无活体队友 → 打印一行并 offer `close`」，两半都没定义——什么 bump `last_seen_at`、怎么数活体队友。本宿主连 `TaskList` 都没有，`ListAgents` 只返回 agent id，`roles[]` 里任何一个名字都对不上一个活进程，所以「无活体队友」在本宿主**不可判定**。现在拆成两个条件并各自给判法：条件 1 是时钟，并明写 `last_seen_at` 只在 Phase 0 被 bump，它记的是「skill 最后一次被调用」而不是「任何人最后一次干活」——连续干活三周不重新调用的团队会读作陈旧，这正是要「问」不要「关」的理由；条件 2 只有宿主能按 `roles[]` 里的名字寻址队友时才可判，`teammates: false` 的宿主按定义成立（不需要探针），**不可判定时降级为只报不判，什么都不 offer**。不留一句做不到的承诺：`SKILL.md` 的错误处理行也从无条件 offer `close` 改成带不可判定分支。
- **`jj-team` 的宿主能力从一个枚举拆成两个能力位**：`host_mode` 三值（`full` / `codex-degraded` / `generic-degraded`）表达不了「有队友但没有任务板」，而本宿主正是如此——`TeamCreate` / `TaskList` 不存在，`Agent` + `SendMessage` 存在且队友常驻跨轮，于是 `full`（要求 Team/Task API）和 `generic-degraded`（描述串行跑）两个都不真。改为 `capabilities: {teammates, task_board}` 两个独立布尔，**不加第四个枚举值**——那只会把短缺推给下一个宿主。`references/roles.md` 补上 CCteam 角色方法论（垂直切片 / TDD / mock 边界 / Doc-Code Sync / 反幻象协议），只接方法论、不复制花名册，`custodian` 默认不设及其理由一字未改；peer relay 的「不经 team-lead 中转」改为如实描述经 main 中转及**为什么**（名字不可达是宿主事实，不是协议选择）。活账本 `team-session.json` 的 `host_mode: "generic-degraded"` 随之改写为 `capabilities: {teammates: true, task_board: false}`。
