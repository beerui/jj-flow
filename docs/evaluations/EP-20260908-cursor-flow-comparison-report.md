## 样本与口径

只读查询了 Cursor 本机 SQLite 的该 composer 与其 5 个子 composer，并冻结对应 transcript 和 bubble 数据。主要证据是 `bubbleId:<composer_id>:<bubble_id>` 记录；文件 mtime 不参与耗时计算。原始请求中带有凭据的早期内容不进入版本化报告。

- `turnDurationMs` 是宿主直接记录的轮次时长，标记为 `clock_quality=exact`、`timestamp_provenance=artifact`。
- 用户消息 `createdAt` 至最终回复 bubble 的 `createdAt` 是派生区间；终点是最终文本开始出现，未必是流式输出结束。它与 `turnDurationMs` 边界不同，两种值分别保留。
- 后台子任务时长单列；父任务的“已派单”回复不表示开发完成，不与子任务重叠区间重复相加。
- Cursor 导出中的 `modelCallId` 有缺失或不同粒度，本报告不据此推算与 Grok 等价的模型循环数。部分工具正文也未保存在对应字段中，不比较两宿主的总读取字节数。

## 值得吸收的执行方式

1. **带着确定范围交接。** 父任务直接给出目标文件、开发 findings 路径、验收标准和审查重点。第一次交接仅一次 read 和一次 `git status`/`diff --stat`，随后派 reviewer，并写必要状态；没有重新搜索多个 Ralph run。第二个相关任务复用了同一开发与审查会话 ID。
2. **按需读取资料。** 17:31 的 end 读取技能前 80 行，17:54 的 end 读取前 50 行。18:14 的 read 记录正文为空，只保留总行数，不能断言这次确实没有读取正文。相比 Grok review 前置阶段读取大量 skill/persona/schema，按阶段定位资料是可执行的改进。
3. **机械 Git 操作按批执行。** 17:54 的最后一次 shell 将重新暂存、diff check、commit、同步工作分支、合并/推送 dev、切回工作分支用 `&&` 串接。18:14 也把同步和合并合到一次调用。少了模型在每一步之间重新决定下一条命令的回合。
4. **小修由主进程完成。** 两次修 LOW 均由主进程直接改动并验证，没有为轻量修补重新搭建完整团队。这适合目前“主进程＋最多一个子代理”的执行限制。

这里运行的是团队 `.plans/` 工作流与 `/jj-end`，冻结父子工具记录中没有 `ralph_ops` 或 `jj ralph` 命令。因此它没有承担当前 Ralph 的同一组状态/证据操作，不能仅按名称认为二者流程成本完全相同。

## 比较的限制与必须保留的检查

- **宿主/模型请求不同。** 父请求记录模型为 `grok-4.6`；当日子任务的实际工具输入明确选择 `cursor-grok-4.6-xhigh-fast`。保存的父 composer 配置也有 `effort=xhigh`、`fast=true`，但不能把保存配置当作所有历史请求的逐次参数。此前 Grok Build 样本为 Grok 4.6 / high。未做同配置复测，无法区分模型服务与流程各贡献多少提速。
- **也存在返工。** 38 秒 end 中有 `diff --cached --check` 的尾空格失败并修复；52 秒 end 中有 SSH 初始化恢复。较快不代表没有检查或重试。
- **分支方向需要提前明确。** 18:18 用户要求该功能从 master 新拉分支，之后发生 82.119 秒分支修正和 23.714 秒推送。这里记录实际追加工作，不将之前未明确的要求倒推为故意违规。流程应尽早绑定需求与分支，避免到合并后再纠正。
- **批处理要有失败停止。** 17:54 使用了 `&&`；18:14 的多行 Git 命令没有展示同等的逐步失败阻断。可复用批量执行思路，但 runner 必须显式检查每一步退出码、冲突、当前分支和远程结果。
- **用户验收仍独立。** App 内顶部空白的历史问题在实际使用时被发现，后来将 `openWebView` 撤回为外部打开并留 TODO。单测和 build 的通过不等于 App 交互验收完成。
