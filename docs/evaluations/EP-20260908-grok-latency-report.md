## Ralph：大部分时间在模型往返与定位

首轮 53 次模型循环、160 次工具调用，工具结果共 310885 字符。后续补问另计 3 轮、5 次工具。

| `waiting_for_model` | 197.164 s | 22.40% |

| `tool_execution` | 26.824 s | 3.05% |

模型为 `grok-4.6`、`reasoning_effort=high`。两轮结束后上下文占用 170491 token；这是上下文占用，不是累计计费 token。

已核实的耗时来源：

1. **启动即全读拆分资料。** 读取了新版 77 行入口，随后同时读取 `phases.md`、`ops.md`、`artifact-layout.md`、`must-evidence.md`。五次工具返回合计 42092 字符。入口变短没有自动保证按阶段加载资料。证据：`updates.jsonl:4,6,8,12,21`。
2. **locate 输出过大。** 无参数 `locate` 返回 64.5 KB，宿主提示截断，只显示约 21.9 KB；进入模型记录的文本仍有 20574 字符。此时已经读取过 index 与两个候选任务计划。证据：`updates.jsonl:36,38,43`，`chat_history.jsonl:24` 及对应 terminal log。当前 `skills/jj-ralph/scripts/ralph_ops.mjs:296` 仅在传入 `--run-id` 时过滤，否则输出完整 runs；精简输出是待实现建议。
3. **修改前的定位链路很长。** 第一次改业务代码在 `12:17:29.918Z`，距请求 594.769 秒。此前 119 次工具调用，其中 70 次 read、36 次 grep。读取 H5 提交方有排查价值，但同一组函数被分散到多轮取不同区间；不能将全部回读都算作冗余。证据：`updates.jsonl:251,253,264,266,292,303,305,409`。
4. **验收范围返工可提前发现。** `12:21:01.697Z` 首次 accept 失败；`12:21:24.648Z` 尝试 `scope --in ... --out ...`；`12:21:42.902Z` 同一原因再失败。旧 `scope.in` 的四个历史文件仍被要求出现在当前 diff，另一组预览改动又被判为计划外。`updateRunScope` 只追加，`collectClaimedImplementationPaths` 合并历史 `scope.in`，当前 diff 收集不会排除 `scope.out`，所以这次操作无法修正原因。证据：`updates.jsonl:581,587,593`；`src/ralph/state.mjs:1371`；`src/ralph/gates.mjs:361,472,579`。
5. **构建和外部服务不是主要等待来源。** fixtures 45/45 的工具计时 0.558 秒，ESLint 1.886 秒。EverOS 未启动导致一次 2.254 秒失败。两轮 Git AI hooks 共 15.900 秒，包含在工具相关窗口内，不能再与阶段时间重复累加。

本次接受门禁阻断有实际范围依据。改进需要保留越界检测，同时区分整条需求的历史范围、本次续做范围及开始时已存在的其他改动。冻结样本最后停在 `READY_FOR_USER_TEST`，之后的 live run 已有更新，不能称为当前仍被阻断。日志中的 fixtures 和 ESLint 通过也不能替代浏览器验收。

## Review：子代理与父流程都占时间

本轮为 **13 分 50 秒**，父流程 19 次模型循环、42 次工具调用。仅一个 reviewer 子代理，meta 记录 `duration_ms=504627`、65 次工具调用、独立新上下文。这约为父 review 轮次的 60.8%。不是多批 reviewer 反复全量审查。

| review 区间 | 耗时 | 观察 |
| --- | ---: | --- |
| 启动 reviewer 前 | 192.236 s | 9 次模型循环、26 次工具调用；工具直接计时合计仅 1.604 s |
| reviewer | 504.627 s | 一个子代理、65 次工具；缺少内部阶段时间，不能再准确分解 |
| reviewer 返回后 | 133.115 s | 10 次模型循环、15 次工具调用；工具直接计时合计仅 1.450 s |

子代理时长来自 meta，`clock_quality=exact`；前后区间由父事件和 meta 时间戳推导，毫秒精度存在约 0.002 秒舍入差。父轮 `tool_execution=513.211s` 已包含子代理等待，不能再加上 504.627 秒。父流程其余墙钟窗口约 5 分 25 秒，并不都能直接省掉。

已核实的改进点：

1. **前置材料和定位分成了太多往返。** 启动前输出 75683 字节，其中七次 skill/persona/schema 读取占 65656 字节；宿主 review skill 单独占 36496 字节。又检查三个 run、三次无命中的 `updated_at`，分轮探测 Python、准备 host、收集 diff。实际收集的 dirty diff 为三文件、5069 字节。可复用会话已绑定 run，把确定性准备合为一次有停止条件的调用，给 reviewer 明确的任务范围和验证证据。证据：冻结 `updates:384–483`。
2. **后处理有两次可避免的恢复。** 内联 `--host-review-json` 使用了不适用于 PowerShell 的转义，导致 JSON 无效，文本中的 `concurrent` 还被当作命令。改为先写 JSON 文件才成功。随后审查文档替换又因多处匹配失败，缩小锚点后成功。建议提供明确的 JSON 文件参数，确定性追加审查记录。证据：`updates:514,526,546,554`。
3. **范围一致性检查把并发改动混入当前审查。** 子代理 Issues 为空，并明确鉴权文件属于另一任务；`review-record` 仍因整个 dirty tree 中的 `middleware/auth.global.ts` 注入 `F-COMPLIANCE-PLAN`，结果为 `NEEDS_CHANGES`。用户下一轮明确要求一起提交。应针对批准的任务 diff 检查，同时单独呈现并发范围；保留门禁，不能直接忽略计划外文件。证据：`updates:493,530,559`。

独立 reviewer 有价值；本样本无法证明其 65 次调用中哪些可省。优化重点是缩小明确的审查输入和减少父流程机械步骤之间的模型循环，而不是撤掉审查。

## End：三分钟收尾的改进方向

本轮为 **3 分 03 秒**，17 次模型循环、22 次工具调用。

| end 阶段 | 耗时 |
| --- | ---: |
| 模型等待 | 83.765 s |
| 推理输出 | 64.185 s |
| 正文输出 | 1.653 s |
| 工具执行阶段 | 33.168 s |

约 82% 时间在宿主观测的模型阶段。工具直接计时合计 24.716 秒，与工具阶段时间口径不同。`jj-end` 只读了一次，根目录、分支和 remote 预检也只做了一次，不能归因为反复重读整个技能。

具体机会：

1. **减少明确 Git 流程之间的模型往返。** 三次显式 fetch 加两次 pull 有重复取远程数据；但包含这些 fetch 的三个工具调用合计仅 4.663 秒，不是分钟级主因。现有技能在 `skills/jj-end/SKILL.md:182,245,289` 要求这些 fetch；可用有状态检查和失败即停的流程合并必要操作，在 HEAD、工作区或远程引用变化后重新校验。状态改变后的 status 仍有必要。
2. **修正 PowerShell 上游引用模板。** 未加引号的 `@{u}` 被当作 PowerShell 语法，失败后 12.807 秒才启动修正调用。模板使用带引号的 `'@{u}'`，减少命令恢复回合。证据：`updates:590,598`。
3. **让产出符合现有格式要求。** 首次 commit 因 Vue 与 review Markdown 的 Prettier 检查失败；随后列出完整 stash 历史、格式化、重查、重提。失败调用开始至成功 commit 完成为 47.410 秒，其中含必要格式化和验证，不能全算浪费。生成记录应遵守格式，失败恢复只查询本次相关状态；保留提交 hooks。证据：`updates:610,616,622,637`。
